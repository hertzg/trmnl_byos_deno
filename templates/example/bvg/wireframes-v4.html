BVG journey board — wireframes v4 [DROPPED]

Iteration 4 explored merging line alternatives within a leg. Decision: dropped. The HAFAS-backed BVG /journeys endpoint returns each connection as a fully concrete journey — one line per leg, with no native alternatives field. The separate /journeys/:ref/alternatives endpoint exists but is a per-leg lookup that would require additional round-trips and client-side merge logic — i.e. we'd be implementing the behaviour ourselves. Per the directive "if HAFAS doesn't give it, leave it out of scope", merging is not built. Journeys render with one line per leg (v3 convention).

Status: dropped. Sections below are preserved for reference only — they document the rejected design. Active conventions remain v3:
• one row per BVG journey, no client-side merging;
• one transit-line badge per leg;
• repeated near-identical rows (S5 / S7 close in time) are tolerated as the cost of deferring to the API.

6 · Merging rule — when does collapse happen?

Two BVG candidates merge into one alt-group row iff:

  • they share the same walking-leg sequence (start, transfers, end durations match);
  • they share the same transit-leg start & end stops;
  • they differ only by the line name on one or more transit legs;
  • both lines are in the user's accept list (otherwise treat as unrelated journeys);
  • their leave-bys are within a configurable spread (default 15 m) — beyond that they're really separate options.

Example outcomes:
• walk·S5·walk + walk·S7·walk with same stops, 7 m apart → merge
• walk·S5·walk·U2·walk + walk·S7·walk·U8·walk → merge with two alt-groups
• walk·S5·walk + walk·BUS·walk with bus excluded → BUS row hidden, no merge needed
• walk·S5·walk·U2·walk + walk·S5·walk·BUS·walk with bus excluded → S5+U2 only, no merge
